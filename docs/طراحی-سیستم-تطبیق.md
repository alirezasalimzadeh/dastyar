# طراحی فنی سیستم تطبیق (Matching) — دستر

وضعیت: **پیشنهاد طراحی — هنوز هیچ کدی تغییر نکرده است.**
قانون اول: دقت و اعتمادپذیری > تعداد نتیجه. در حالت شک، «نشان ندادن» بهتر از «پیشنهاد نامرتبط» است.

## §۰. وضعیت فعلی (بررسی کد موجود)

موتور فعلی: `src/lib/matching.ts` → `calculateMatch(property, customer)`
مصرف‌کننده‌ها: صفحهٔ «تطبیق» (محاسبهٔ زنده در مرورگر)، تب «تطبیق‌ها» در جزئیات مشتری و فایل (خواندن از جدول `property_matches`).

### مشکلات موجود (با شماره‌گذاری برای پیگیری)
| # | مشکل | عواقب |
|---|---|---|
| ۱ | **فیلتر سخت وجود ندارد.** نوع معامله/دسته/نوع ملک فقط «امتیاز» هستند (۱۵/۱۰/۱۰) | جفت ناسازگار (مثلاً متقاضی خرید در برابر فایل اجاره) باز هم ۴۰–۶۰٪ می‌گیرد و نمایش داده می‌شود |
| ۲ | **نقش طرفین اصلاً بررسی نمی‌شود** و جدول `COMPLEMENTARY` منطقی نیست (`buy → ['sell','buy']` یعنی متقاضی خرید با فایلِ درخواستِ خرید هم «تطبیق» دارد) | درخواست در برابر درخواست، عرضه در برابر عرضه = تطبیق |
| ۳ | تمایزی بین «ترجیح نداده‌ام» و «داده‌ای نیست» نیست: هر فیلد بدون مقداری ۵۰٪ امتیاز کاملش را می‌گیرد (موقعیت، بودجه، متراژ، اتاق، طبقه، امکانات) | هر جفت ناسازگار ~۳۰–۴۰ امتیاز «رایگان» جمع می‌کند |
| ۴ | ترجیحات مشتری با **نوع ملکِ فایل** خوانده می‌شود (`getTypePrefs(customer, property.property_type)`) | مشتری‌ای که فقط ترجیحات آپارتمان را پر کرده، از فایل مغازه ۵۰٪ بودجه + ۵۰٪ متراژ + ۵۰٪ اتاق دریافت می‌کند |
| ۵ | موقعیت مشتری در فرم فقط شهرستان/محله ذخیره می‌شود (شهر نه) اما موتور `city_id` می‌خواند که هرگز نوشته نمی‌شود؛ `preferred_city_ids` اصلاً خوانده نمی‌شود | سلسله‌مراتب استان→شهرستان→شهر→محله در عمل به یک سطح (شهرستان) فشرده می‌شود |
| ۶ | نقشهٔ امکانات فایل ناقص است: از ۲۶ امکاناتی که مشتری می‌تواند بخواهد، فقط ۸ تا ستون فایل دارند | آتشکده/سونا/کرکره برقی/تابلوخور/سرویس بهداشتی/چاه آب و... **همیشه** «نقص» شمرده می‌شوند حتی اگر فایل داشته باشد |
| ۷ | بررسی‌های facing / commercial_location / structure_type / frontage **کود مرده** هستند (فایل این ستون‌ها را ندارد، `propVal` همیشه undefined است) | کاربر فکر می‌کند بررسی می‌شود؛ در واقع هیچ اتفاقی نمی‌افتد |
| ۸ | متراژ فایل با `land_area ?? building_area` خوانده می‌شود | برای آپارتمانی که متراژ زمین هم دارد، متراژ زمین با بازهٔ مشتری مقایسه می‌شود |
| ۹ | جدول `property_matches` **هیچ‌جا نوشته نمی‌شود** (فقط خوانده می‌شود) | تب «تطبیق‌ها» در جزئیات‌ها خالی/قدیمی است؛ فقط صفحهٔ تطبیق محاسبهٔ زنده دارد (۱۰۰×۱۰ جفت در مرورگر) |
| ۱۰ | مقیاس تیرها (۸۵/۷۰/۵۵/۴۰) با اعداد تورم‌یافتهٔ #۳ هم‌خوانی ندارد | جفت‌های نامرتبط به‌عنوان «ضعیف/متوسط» نمایش داده می‌شوند |
| ۱۱ | شراکت: بودجه فقط ثابت ۰.۵/۰.۶ می‌گیرد | هیچ منطق واقعی ندارد |
| ۱۲ | ودیعهٔ صفر/غیاب در فایل اجاره (اجارهٔ خالص ماهانه) به‌عنوان «ارزان‌تر از حداقل» جریمه می‌شود | فایل «بدون ودیعه» که برای مشتری ودیعه‌دار جذاب است، تنبیه می‌شود |
| ۱۳ | مدل دادهٔ «ناشناخته / نیازی نیست / الزامی / مطلوب» وجود ندارد | عمدهٔ مشکلات بالا ریشه در همین دارد |
| ۱۴ | توضیح تطبیق = چیپ‌های سادهٔ تیک/صندل + چند خط تفاوت ناقص (اعداد خام تومان) | «چرا این عدد؟» قابل پاسخ نیست |

## §۱. معماری موتور جدید

یک لولهٔ پنج‌مرحله‌ای؛ هر مرحله ورودی/خروجی مشخص دارد و **مرحله‌های بعدی فقط روی جفت‌هایی اجرا می‌شوند که مرحله قبل را رد کرده‌اند**:

```
 ┌─────────────┐   ┌──────────────────┐   ┌───────────────────┐
 │ ۱. نرمال‌   │ → │ ۲. فیلتر سخت     │ → │ ۳. محدودیت‌های    │
 │   سازی      │   │    (REJECT؟)     │   │    قوی (VETO؟)    │
 └─────────────┘   └──────────────────┘   └───────────────────┘
 Customer/Property          جفت ناسازگار ← رد (با دلایل)          جفت دور ← رد (با دلایل)
 MatchProfile (هر دو جهت)                ┌───────────────────┐   ┌───────────────────┐
                                         │ ۴. امتیازدهی      │ → │ ۵. توضیح + تیر +  │
                                         │    مؤلفه‌ای ۰..۱   │   │    رتبه‌بندی       │
                                         └───────────────────┘   └───────────────────┘
```

ساختار فایل‌ها (فقط بخش تطبیق می‌سوزد، هیچ صفحه‌ای دست‌نخورده می‌ماند):

```
src/lib/matching/
  config.ts       ← همهٔ وزن‌ها، جداول سازگاری، آستانه‌ها (تنظیمات در یک نقطه)
  normalize.ts    ← Customer|Property → MatchProfile (دو تابع، یک شکل مشترک)
  hard.ts         ← ماتریس معامله/نقش + دسته + سازگاری نوع ملک
  constraints.ts  ← تابع‌های فاصله (قیمت/متراژ/اتاق/موقعیت) + آستانه‌های veto
  score.ts        ← مؤلفه‌ها، وزن‌ها، امتیاز نهایی، تیر، اعتماد
  explain.ts      ← تولید ✓ / ⚠ / ℹ از همان مقادیر محاسبه‌شده
  index.ts        ← matchPair(a, b): MatchOutput + calculateMatch (ورپر سازگاری با امضای فعلی)
```

**`MatchProfile`** (نمای مشترک دو طرف — قلب «دو جهت مشترک»):
```
{
  side: 'customer' | 'property',
  tx: 'buy'|'rent'|'sell'|'partnership' | null,
  role: 'buyer'|'seller'|'owner'|'applicant'|'builder' | null,
  category, types[],                       // مشتری: preferred_*؛ فایل: category/property_type
  location: { province?, county?, city?, neighborhood?, cityList[] },
  money: { price?, deposit?, rent?, landValue?, share?, budget{min,max}, deposit{min,max}, rent{min,max} },
  specs: Record<key, { value, bound: 'min'|'max'|'exact'|'any' }>,   // متراژ/زمین/زیربنا/اتاق/دهنه/عرض گذر/سن...
  features: Record<key, 'required'|'preferred'|'absent'>,
  completeness: { txOk, categoryOk, hasMoney, hasLocation, hasSpecs, hasFeatures }
}
```
نکتهٔ کلیدی #۴ رفع می‌شود: ترجیحات مشتری در normalize برای **نوع سازگار برنده** انتخاب می‌شود (مطابق §۱۰)، نه صرفاً نوع فایل.

### دو جهت (مرحله ۹)
`matchPair(profileA, profileB)` تقارنی است: هر طرف فقط از فیلدهای `MatchProfile` می‌خواند.
`customer→property` و `property→customer` = همان تابع با دو profile. کلمات توضیح بر اساس `side` تولید می‌شوند
(«فایل ۲۰٪ گران‌تر از بودجهٔ مشتری» / «بودجهٔ مشتری ۰٪ کمتر از قیمت فایل»).

### ذخیره‌سازی
`property_matches` فعلاً یتیم است. در فاز ۳ (پس از تأیید طراحی) یک `persistMatches(entity)` بعد از
ذخیره/ویرایش مشتری یا فایل، جفت‌های با امتیاز ≥ آستانهٔ نمایش (حداکثر ۲۰ مورد به‌ازای هر رکورد) را upsert می‌کند
و بقیه را حذف؛ ساختار جدول فعلی کافی است (score/factors/differences) + یک ستون `explanation` jsonb پیشنهاد می‌شود.

## §۲. فیلتر سخت (قبل از هر امتیازی)

### ۲.۱ ماتریس معامله × نقش (دوطرفه)
نقش‌ها در اپ ثابت‌اند: buy→buyer، sell→seller، rent→owner|applicant، partnership→owner|builder.
پس سازگاری کاملاً با جفت (نوع، نقش) مشخص است:

| مشتری | فایل | منطق |
|---|---|---|
| buy / buyer (متقاضی خرید) | sell / seller (فایل فروش) | خریدار ↔ عرضه |
| sell / seller (فروشنده) | buy / buyer (فایل خرید/درخواست) | فروشنده ↔ تقاضا |
| rent / applicant (متقاضی اجاره) | rent / owner (فایل مالکِ مُستاجرکننده) | مستأجر ↔ عرضه |
| rent / owner (مالکِ مُستأجربه) | rent / applicant (فایل درخواست اجاره) | عرضه ↔ تقاضا |
| partnership / owner (مالک زمین) | partnership / builder (فایل سازنده) | زمین ↔ سازنده |
| partnership / builder (سازنده) | partnership / owner (فایل مالک زمین) | سازنده ↔ زمین |

**هر ترکیب دیگر = REJECT** (درخواست↔درخواست هم‌نوع، عرضه↔عرضه، buy↔rent و...).
**تأیید شده در این نشست:** در داده‌های دستر **هر دو جور فایل** (عرضه و تقاضا) ثبت می‌شود؛
پس هر شش جفت بالا در عمل استفاده می‌شود. جفت‌های ردشده عمدی‌اند: مثلاً فایل «دنبال خرید»
(خرید/متقاضی) با مشتری «دنبال خرید» (buy/buyer) تطبیق **نمی‌گیرد** چون هر دو تقاضا هستند —
فایل تقاضای خرید فقط با مشتری **فروشنده** می‌نشیند و بالعکس.
اگر مشتری `transaction_intention` یا `transaction_role` ندارد → جفت «بدون محاسبه» با وضعیت **پروفایل ناقص** (نه تطبیق، نه رد؛ در توضیح: «نوع معامله مشتری ثبت نشده»).

### ۲.۲ دسته‌بندی
مساوی دقیق: مسکونی↔مسکونی، تجاری↔تجاری، صنعتی↔صنعتی، کشاورزی↔کشاورزی، اداری↔اداری.
متفاوت = REJECT. (بدون استثنا — در نسخهٔ اول.)

### ۲.۳ سازگاری نوع ملک (§۱۰ را ببینید)
مطابقت با جدول سازگاری: exact/close/partial می‌گذرند؛ بقیه REJECT.
مشتری چند نوع دارد → بهترین سطح بین لیست. مشتری بدون نوع → بدون محدودیت نوع (فقط دسته) + ℹ «نوع ملک مشخص نشده».

## §۳. محدودیت‌های قوی (Strong Constraints) — آستانهٔ VETO

بعد از فیلتر سخت، هر محدودیت یک **تابع فاصله** دارد؛ اگر فاصله از آستانهٔ veto رد شود، جفت **رد** می‌شود (بدون امتیاز نهایی).
مقادیر غیرمردود، امتیاز ۰..۱ خود را به مؤلفهٔ مربوطه می‌دهند (در §۶).

| محدودیت | مقایسه | تابع فاصله | آستانهٔ veto |
|---|---|---|---|
| قیمت (خرید/فروش) | `sale_price` (یا `owner_requested_price` اگر صفر بود) با `[budget_min, budget_max]` | §۷ | گران‌تر بودن ≥ **۵۰٪** بیش از سقف |
| ودیعه (اجاره) | `deposit_price` با `[deposit_min, deposit_max]` | §۷ | گران‌تر ≥ **۵۰٪** |
| اجاره ماهانه (اجاره) | `monthly_rent` با `[rent_min, rent_max]` | §۷ | گران‌تر ≥ **۵۰٪** |
| متراژ (مسکونی/تجاری/اداری) | `building_area` با `[min_area, max_area]` | §۸ | بزرگ‌تر ≥ **۵۰٪** بیش از سقف |
| متراژ زمین (زمین/باغ/کشاورزی) | `land_area` با `[min_area, max_area]` | §۸ | هم‌بالا |
| متراژ زمین (صنعتی) | `land_area` با `[min_land_area, max_land_area]` | §۸ | هم‌بالا |
| متراژ سالن (صنعتی) | `building_area` با `min_hall_area` (فقط سقف) | §۸ | بزرگ‌تر ≥ ۵۰٪ |
| اتاق (مسکونی/اداری) | `bedrooms ?? rooms` با `min_rooms` | کمبود ۱ اتاق → امتیاز ۰.۴ + ⚠ | کمبود ≥ **۲ اتاق** |
| موقعیت | سلسله‌مراتب §۹ | — | شهرستان/شهر/محلهٔ **شناخته‌شدهٔ متفاوت** |
| شراکت | `participation_price` فایل با `land_value` مشتری | نسبت | فقط ⚠ در اختلاف > ۳× (veto نیست — بُعد مشترک نیست) |

قاعدهٔ مهم: veto فقط وقتی اعمال می‌شود که **فیلد فایل هم مشخص باشد**. فایل بدون قیمت = veto نیست (→ ℹ «قیمت ثبت نشده»).

### مثال‌های کاربردی (از خواستهٔ شما)
- سقف ۵ میلیارد، فایل ۵.۲ → d=4٪ → s=1−2·0.04=**0.92** → می‌ماند، امتیاز مالی عالی.
- سقف ۵ میلیارد، فایل ۱۲ → d=140٪ → s=0 → **VETO** («قیمت ۱۴۰٪ بالاتر از سقف بودجه»).
- بازه ۹۰–۱۲۰ متر، فایل ۱۱۰ → **1.0**؛ ۱۲۵ → **0.92**؛ ۱۵۰ → **0.5**؛ ۳۰۰ → d=150٪ → **VETO**.

## §۴. ترجیحات نرم (Soft Preferences) و سطوح اهمیت

سطح اهمیت از **معنای کلید** استخراج می‌شود — بدون تغییر ساختار داده:

| سطح | قاعدهٔ تشخیص | رفتار «فایل ندارد/ثبت نشده» |
|---|---|---|
| **REQUIRED** | کلیدهای `min_*` (اتاق، دهنه، عرض گذر، سالن)، `has_commercial=true`، `needs_permit=true` | قابل تأیید نبودن = ۰.۵ + ⚠ «در فایل ثبت نشده — نیاز به بررسی» |
| **PREFERRED** | چک‌باکس‌های امکانات، `floor_preference≠any`، `facing≠any`، `structure_type`، `commercial_location` | فایل صریحاً ندارد = ۰ ( واقعی)؛ ستون فایل اصلاً وجود ندارد = ۰.۵ + ℹ |
| **OPTIONAL** | `units_per_floor`، `total_floors`، `water_quota`، سقف‌های `max_*` | وزن پایین، جریمهٔ سبک |

> اگر روزی بخواهید سطح یک فیلد را دستی عوض کنید، `config.ts` جدول استثنا دارد — بدون مهاجرت داده.

## §۵. وزن مؤلفه‌ها (مرکزی در `config.ts`)

| مؤلفه | وزن | چرا این وزن |
|---|---|---|
| Core (نوع معامله/دسته/نوع ملک) | **۲۰** | فیلتر سخت رد شده؛ اینجا فقط درجهٔ نوع ملک (exact/close/partial) رتبه می‌دهد |
| Financial (مالی) | **۲۵** | در معاملات املاک، قیمت تصمیم‌ساز اول است؛ فایل گران = بی‌استفاده حتی با همهٔ امکانات |
| Location (موقعیت) | **۲۰** | بازار محلی است؛ اما یک پله زیر قیمت |
| Physical (مشخصات فیزیکی) | **۲۰** | متراژ/اتاق/طبقه؛ کاربردپذیری |
| Features (امکانات) | **۱۵** | امکانات را متعادل می‌کنند، تصمیم نمی‌گیرند |

مجموع = ۱۰۰. همهٔ وزن‌های زیرمجموعه‌ها (زیرمقدارهای مالی، فیزیکی، وزن هر امکانات) هم در همان `config.ts`.

## §۶. فرمول نهایی

```
برای هر جفت (c, p):
  H = hardFilter(c, p)                    // §۲
  اگر H رد → MatchOutput{ eligible:false, rejectReasons:H.reasons } → پایان

  S = strongConstraints(c, p)             // §۳
  اگر S.veto → MatchOutput{ eligible:false, rejectReasons:S.reasons } → پایان

  s_core   = levelScore(H.typeLevel)      // exact=1.0 ، close=0.8 ، partial=0.6 ، بدون‌نوع=1.0
  s_fin    = financialScore(c, p)         // §۷
  s_loc    = locationScore(c, p)          // §۹
  s_phys   = Σ w_sub·s_sub / Σ w_sub(فعال)  // متراژ(0.5) + اتاق(0.3) + طبقه(0.2) + سن(0.1*) ...
  s_feat   = Σ w_f·s_f / Σ w_f(درخواستی)   // §۱۱

  score    = round( 20·s_core + 25·s_fin + 20·s_loc + 20·s_phys + 15·s_feat )
  trust    = وزن مؤلفه‌های فعال / 100     // «اطمینان»: دادهٔ چندانی داریم؟
  tier     = §۱۳

  اگر ≥۲ مورد REQUIRED «غیرقابل تأیید» باشند → score = min(score, 74) + ⚠ «اطلاعات فایل ناقص است»
```

- مؤلفه‌ای که مشتری درباره‌اش حرفی نزده (مثلاً بودجه نپرده) → `s = 0.5` خنثی؛ در trust کسر می‌شود.
- **امتیاز نهایی نمی‌تواند veto را دور بزند** چون veto قبل از فرمول اجرا می‌شود و امتیاز اصلاً ساخته نمی‌شود.
- «مشتری کاملاً خالی» (فقط نوع معامله/دسته/نوع دارد) → score = 20 + (25+20+20+15)×0.5 = **۶۰** با trust «کم» —
  یعنی «سازگار، ولی چیزی نمی‌دانیم» نه «۱۰۰٪ تطبیق».

### ترازهای فاصله در فرمول‌های §۷/§۸
```
fit(v, [lo, hi]) =
  v ∈ [lo, hi]            → 1.0
  v > hi:  d=(v−hi)/hi    → max(0, 1 − 2d)     // ۵۰٪ عبور = 0 = veto
  v < lo:  d=(lo−v)/lo    → max(0.4, 1 − d)    // فقط lo تا ۵۰٪ ارزان‌تر هم کف 0.4 دارد
  hi نامشخص و lo مشخص    → فقط قانون v<lo
  lo نامشخص و hi مشخص    → فقط قانون v>hi
  هر دو نامشخص            → 0.5 (خنثی)
```
دلیلی که عبورِ گران‌تر تندتر از عبورِ ارزان‌تر افت می‌کند: فایل گران‌تر از سقف بودجه عملاً خارج از دسترس است؛
فایل ارزان‌تر از کف هنوز قابل معامله است (صرفه برای خریدار).

## §۷. محاسبهٔ فاصلهٔ قیمت

- **خرید/فروش:** `s_fin = fit(price, [budget_min, budget_max])`؛ price = `sale_price`، اگر خالی بود `owner_requested_price`.
- **اجاره:** `s_fin = 0.6·fit(deposit) + 0.4·fit(rent)` روی زیرمقدارهای **فعال** (اگر مشتری فقط اجاره داد، وزن اجاره ۱).
  -حالت خاص: ودیعهٔ فایل صفر/غیرثبت (اجارهٔ خالص ماهانه) → زیرمقدار ودیعه **حذف** می‌شود (نه جریمه) + ℹ «بدون ودیعه — اجارهٔ ماهانه خالص». (رفع #۱۲)
- **شراکت:** `s_fin = 0.5` خنثی + بررسی نرم: اگر هر دو `participation_price` و `land_value` باشند و نسبت > ۳ → ⚠ (بدون veto — بُعد مشترک دقیق نیست).
- اعداد در توضیح با `formatMoneyShort` («۵ میلیارد»، «۴۸۰ میلیون») نه تومان خام.

## §۹. تطبیق موقعیت (سلسله‌مراتبی)

ورودی‌ها:
- مشتری: `prefs.location.county_id`، `prefs.location.neighborhood_id`، `preferred_city_ids[]` (اگر پر شده)
- فایل: `province_id, county_id, district_id, city_id, neighborhood_id` (هر کدام ممکن است خالی باشد)

```
آستانه (veto) — فقط وقتی محل فایل «شناخته‌شده» است:
  · county فایل ≠ county مشتری                     → REJECT «شهرستان متفاوت»
  · neighborhood فایل ≠ neighborhood مشتری         → REJECT «محلهٔ متفاوت»
  · مشتری شهرهایی مشخص کرده و city فایل ∈ خارج از آن‌ها → REJECT «شهر خارج از محدوده»

امتیاز (غیرمردود):
  محلهٔ یکسان                                  → 1.00
  شهرستان یکسان + (شهر فایل ∈ لیست مشتری یا لیست خالی) → 0.75
  شهرستان یکسان + شهر فایل مشخص و خارج از لیست      → 0.45 + ⚠
  شهرستان یکسان + شهر فایل نامشخص                 → 0.60
  county فایل نامشخص + city فایل ∈ لیست مشتری      → 0.70
  county و city فایل هر دو نامشخص                  → 0.50 + ℹ «موقعیت فایل ثبت نشده»
  مشتری هیچ موقعیتی ندارد                          → مؤلفه حذف → 0.5 خنثی + ℹ
```
- «همان استان» به‌تنهایی امتیاز نمی‌دهد (رفع دقیقاً همان شکایتی که مطرح کردید):
  تطبیق استان فقط وقتی county/city فایل خالی‌اند دیده می‌شود و حتی آن‌وقت سقف 0.3 + ⚠ «فاصلهٔ جغرافیایی».
- خیابان/محدوده: تا ستون `street` در دیتابیس ساخته نشود غیرقابل محاسبه است؛ طوری طراحی شده که بعداً
  یک سطح دقیق‌تر (خیابان/محدوده) با امتیاز 1.0 + ℹ به همین تخته اضافه شود.

## §۱۰. سازگاری نوع ملک (جدول قابل توسعه)

در `config.ts` — جفت‌های دوطرفه و صریح؛ **هر جفتی که در جدول نیست = REJECT** (محتاطانه، مطابق قاعدهٔ اول):

| سطح | جفت‌ها |
|---|---|
| **exact (1.0)** | هر نوع ↔ خودش |
| **close (0.8)** | آپارتمان↔پنت‌هاوس، آپارتمان↔سوئیت، آپارتمان↔برج، سوئیت↔پنت‌هاوس، برج↔سوئیت، خانه ویلایی↔ویلا، خانه ویلایی↔کلنگی، ویلا↔کلنگی، کارخانه↔کارگاه، کارخانه↔سوله، کارگاه↔سوله، انبار↔گاراژ |
| **partial (0.6)** | آپارتمان↔خانه ویلایی، آپارتمان↔ویلا، مغازه↔غرفه پاساژ، مغازه↔زیرزمین تجاری، مغازه↔زمین تجاری، زمین مسکونی↔کلنگی، زمین مسکونی↔خانه ویلایی، زمین کشاورزی↔باغ، زمین صنعتی↔کارخانه، زمین صنعتی↔کارگاه، آپارتمان اداری↔آپارتمان |

- مشتری [آپارتمان، مغازه] و فایل پنت‌هاوس → best = close(0.8).
- مشتری [آپارتمان] و فایل مغازه → هیچ سطحي → REJECT («نوع ملک نامرتبط: آپارتمان ↔ مغازه»).
- افزودن/حذف هر جفت = یک خط در جدول (قابل توسعه بدون لمس منطق).

## §۱۱. امتیازدهی امکانات

برای هر امکاناتی که مشتری **درخواست** کرده (`=true` در ترجیحات نوع سازگار):
```
s_f = فایل دارد (ستون boolean = true)          → 1.0
      فایل صریحاً ندارد (ستون = false)           → 0   + ⚠ «بدون پارکینگ»
      ستون در فایل اصلاً وجود ندارد              → 0.5 + ℹ «در فایل ثبت نشده»
امکاناتی که مشتری درخواست نکرده: هیچ جریمه‌ای.
s_feat = Σ w_f·s_f / Σ w_f
```
وزن‌ها (مرکزی در `config.ts` — نمونه): پارکینگ ۳، آسانسور ۲، نگهبانی ۲، انباری ۲، تابلوخور ۲،
بالکن/کرکره برقی/سرویس بهداشتی/آتشکده/جکوزی/آبنما/آلاچیق/باربیکیو/سونا/سرایداری ۱،
حیاط/باغ/چهاردیواری/چاه آب/فضای اداری/جرثقیل/آب/برق/گاز ۲، استخر ۱.
نقشهٔ «کدام امکانات در فایل قابل تأییدند» هم در همین جدول:
`parking, storage, elevator, balcony, yard, garden, pool, security` (بقیه تا ستون جدید = قابل تأیید نیستند → رفع #۶ به‌صورت شفاف).

## §۱۲. داده‌های ناقص — چهار حالت

| حالت | تشخیص | رفتار |
|---|---|---|
| **Unknown/Not specified** (مشتری حرف نزده) | فیلد در ترجیحات خالی | حذف از مخرج مؤلفه؛ ۰.۵ خنثی در فرمول؛ trust کم می‌شود؛ در توضیح: «مشتری ترجیحی ثبت نکرده» |
| **Not required** | مشتری فیلد را `any`/«فرقی ندارد» کرده | امتیاز کامل (1.0) — محدودیت نیست |
| **Required** | `min_*` یا چک‌باکس الزامی | تابع §۳؛ اگر فایل ثبت نکرده → 0.5 + ⚠ و شمارش در «غیرقابل تأیید» |
| **Preferred** | امکانات/ترجیحات | تابع §۱۱ |

اصل: **NULL = عدم تطبیق نیست.** NULL در طرف مشتری = آزادی انتخاب؛ NULL در طرف فایل = «تأیید نشده» (نه «ندارد») —
مگر آنکه ستون فایل boolean باشد و صریحاً false باشد.

## §۱۳. تیرها و آستانه‌های نمایش (و دلیل آن‌ها)

با فرمول جدید، «خط مبنا» یک جفت کاملاً بدون داده ≈ ۵۵–۶۰ (هر مؤلفه خنثی ۰.۵ + core).
هر ۱۰ امتیاز بالاتر از مبنا ≈ یک گروه قوی+نرم که واقعاً تأیید شده. بر این پایه:

| تیر | بازه | معنای عملی |
|---|---|---|
| **Excellent** | ≥ **85** | همهٔ محدودیت‌های قوی داخل بازه + اکثر ترجیحات تأیید؛ «همین حالا تماس بگیر» |
| **Good** | **70–84** | سازگار با ۱–۲ هشدار قابل گفت‌وگو (مثلاً ۱۰٪ عبور ودیعه) |
| **Fair** | **55–69** | سازگار ولی با ضعف محسوس یا داده‌های کم |
| **Weak** | **40–54** | زیر خط مبنا؛ فقط در حالت «نمایش پیشرفته» |
| **Hidden** | < 40 | پیش‌فرض نمایش داده **نمی‌شود** |

- آستانهٔ پیش‌فرض نمایش: **55** (اسلایدر فعلی 40 → 55).
- توجیه: زیر 55 یعنی حتی از «جفتی که هیچی از آن نمی‌دانیم» هم ضعیفتر است — نمایش آن فقط نویز است.
  در نسخهٔ اول (دقت > فراوانی) این آستانهٔ درست است؛ با جمع شدن دادهٔ بهتر می‌توان به 50–60 تنظیم کرد (یک عدد در `config.ts`).
- رتبه‌بندی: `score ↓` → `تعداد ⚠ ↑` → `فاصلهٔ مالی از بازه ↓` → `تازه‌بودن فایل`.

## §۱۴. ساختار خروجی Match

```ts
interface MatchOutput {
  eligible: boolean;
  rejectReasons?: string[];          // وقتی رد شده — دقیق و قابل نمایش
  score?: number;                     // 0–100
  tier?: 'excellent' | 'good' | 'fair' | 'weak';
  confidence?: 'high' | 'medium' | 'low';   // trust = وزن مؤلفه‌های فعال
  components?: { key: 'core'|'financial'|'location'|'physical'|'features';
                 weight: number; value: number; active: boolean }[];
  explanation?: { positives: string[]; warnings: string[]; unverifiable: string[] };
}
```
سازگاری عقب: `calculateMatch(property, customer)` امضای فعلی را نگه می‌دارد و `MatchOutput` را به
`{score, factors, differences}` فعلی می‌سازد → هیچ صفحه‌ای در فاز اول نمی‌سوزد.

## §۱۵. تولید توضیح تطبیق

هر زیرمقدار وقتی امتیاز می‌گیرد، **همزمان** یک سطر توضیح با مقادیر واقعی تولید می‌کند (نه ساختگی):
- `fit` در-range → `✓ قیمت داخل بودجه (۴.۸ میلیارد در بازهٔ ۴ تا ۵ میلیارد)`
- `fit` عبور → `⚠ ودیعه ۲۰٪ بالاتر از سقف (۳۰۰ میلیون در برابر ۲۵۰ میلیون)`
- location → `✓ محلهٔ موردنظر` / `✓ همان شهرستان (شهر: روباط‌کریم)`
- features → `✓ پارکینگ، آسانسور` / `⚠ بدون انباری`
- unverifiable → `ℹ طبقهٔ فایل ثبت نشده — نیاز به بررسی`
نمایش در UI: رینگ امتیاز + تیر + ۳–۶ سطر ✓ + ⚠های برجسته + ℹ در بخش «نیاز به بررسی».
(ساختار `differences` فعلی حفظ می‌شود؛ `positives` جدید می‌شود.)

## §۱۶. رتبه‌بندی
1. جفت‌های ردشده اصلاً وارد لیست نمی‌شوند (نه با امتیاز ۰ — چون «۰٪» خودش ادعاست).
2. جفت‌های باقیمانده بر حسب score نزولی؛ تساوی → کمتر ⚠ → فاصلهٔ مالی کم‌تر.
3. صفحهٔ تطبیق: پیش‌فرض `≥55`، اسلایدر ۴۰–۱۰۰ برای حالت پیشرفته؛ برچسب تیر روی هر کارت.
4. در تب «تطبیق‌ها» جزئیات مشتری/فایل: فقط `excellent+good` (حداکثر ۵) — همان ۵ مورد فعلی ولی واقعی.

## §۱۷. مثال واقعی، مرحله‌به‌مرحله

### مثال A — مشتری → فایل‌ها
**مشتری A:** خرید/متقاضی، مسکونی، [آپارتمان]، شهرستان روباط‌کریم (بدون محله/شهر)، بودجه ۴–۵ میلیارد،
متراژ ۹۰–۱۲۰، حداقل ۲ اتاق، پارکینگ + آسانسور (PREFERRED).

**فایل P1:** فروش/مالک، مسکونی، آپارتمان، روباط‌کریم، ۴.۸ میلیارد، زیربنا ۱۰۵، ۲ خواب، پارکینگ✓ آسانسور✓.

| مرحله | نتیجه |
|---|---|
| Hard | buy/buyer ↔ sell/seller ✓ · مسکونی=مسکونی ✓ · آپارتمان↔آپارتمان exact ✓ → **می‌گذرد** |
| Strong | قیمت: ۴.۸ ∈ [۴,۵] → 1.0 · متراژ: ۱۰۵ ∈ [۹۰,۱۲۰] → 1.0 · اتاق: ۲≥۲ → 1.0 · موقعیت: county یکسان → veto نیست |
| core | 1.0 → ۲۰ |
| fin | 1.0 → ۲۵ |
| loc | county یکسان + لیست شهر خالی → 0.75 → ۱۵ |
| phys | متراژ 1.0(0.5) + اتاق 1.0(0.3) → 1.0 → ۲۰ |
| feat | پارکینگ(3)+آسانسور(2) هر دو ✓ → 1.0 → ۱۵ |
| **نهایی** | **95 — Excellent** (trust: high) |
| توضیح | ✓ قیمت داخل بودجه (۴.۸ میلیارد) · ✓ متراژ مناسب (۱۰۵ متری) · ✓ ۲ خواب · ✓ پارکینگ، آسانسور · ℹ محله ثبت نشده — همان شهرستان تأیید شده |

**فایل P2:** فروش/مالک، آپارتمان، شهرستان کرج، ۱۲ میلیارد، ۲۵ متری، ۴ خواب، استخر.

| مرحله | نتیجه |
|---|---|
| Hard | ✓ می‌گذرد (نوع/دسته/معامله سازگار) |
| Strong | قیمت: d=(۱۲−۵)/۵=**140٪** → **VETO** · متراژ: d=**108٪** → **VETO** · موقعیت: county کرج ≠ روباط‌کریم → **VETO** |
| **نهایی** | **رد می‌شود** — دلایل: «قیمت ۱۴۰٪ بالاتر از سقف بودجه» · «متراژ ۱۳۰ متر بیشتر از سقف» · «شهرستان متفاوت» — هرچند استخر و ۴ خواب دارد، اصلاً لیست نمی‌شود. (دقیقاً سناریوی مورد خواستهٔ شما) |

**فایل P3:** اجاره/مالک، تجاری، مغازه، روباط‌کریم → **Hard REJECT**: «متقاضی خرید ↔ فایل اجاره — نوع معامله/نقش ناسازگار».
(در سیستم فعلی همین فایل با موقعیت خوب + امکانات، ~۴۵٪ می‌گرفت.)

### مثال B — فایل → مشتری (جهت دوم، اجاره)
**فایل Q:** اجاره/مالک، آپارتمان، روباط‌کریم، ودیعه ۳۰۰ میلیون، اجاره ۸ میلیون، ۸۰ متری، ۱ خواب.
**مشتری B:** اجاره/متقاضی، [آپارتمان]، روباط‌کریم، ودیعه ۱۵۰–۲۵۰ میلیون، اجاره ۵–۱۰ میلیون، ۷۰–۱۰۰ متری، حداقل ۲ اتاق.

| مرحله | نتیجه |
|---|---|
| Hard | rent/applicant ↔ rent/owner ✓ · آپارتمان exact ✓ → می‌گذرد |
| Strong | ودیعه: d=(۳۰−۲۵۰)/۲۵۰=**20٪** → s=1−0.4=**0.6** (veto نیست) · اجاره: ۸ ∈ [۵,۱۰] → 1.0 · متراژ: ۸۰ ∈ [۷۰,۱۰۰] → 1.0 · اتاق: کمبود ۱ → **0.4 + ⚠** (veto نیست؛ ≥۲ بود veto) |
| fin | 0.6×0.6 + 0.4×1.0 = **0.76** → ۱۹ |
| loc | county یکسان → 0.75 → ۱۵ |
| phys | (0.5×1.0 + 0.3×0.4)/0.8 = **0.775** → ۱۵. |
| feat | مشتری امکاناتی درخواست نکرده → خنثی 0.5 → ۷.۵ |
| **نهایی** | **77 — Good** (trust: medium) |
| توضیح | ✓ اجاره ماهانه در بودجه (۸ میلیون) · ✓ متراژ مناسب (۸۰ متری) · ⚠ ودیعه ۲۰٪ بالاتر از سقف (۳۰۰ در برابر ۲۵۰ میلیون) · ⚠ یک اتاق کمتر از حداقل |

این مثال نشان می‌دهد جفتی با دو ضعف واقعی، «عالی» نمی‌شود (در سیستم فعلی می‌شد: ودیعه 0.4×20 + بقیه خنثی‌ها ≈ ۵۵–۶۰ «متوسط/ضعیف» ولی با دلایل مبهم).

## §۱۸. مشکلات و محدودیت‌های صریح الگوریتم

1. **رقابت «ناقص بودن» دادهٔ فایل:** فایل‌های کم‌داده (بدون موقعیت/قیمت/امکانات) امتیاز خنثی ۰.۵ می‌گیرند و می‌توانند جلوی فایل‌های کامل‌تر بی‌ضعف قرار بگیرند.
   → مهار: سقف 74 برای «≥۲ مورد REQUIRED غیرقابل تأیید» + نمایش ℹ. ریشه‌ای‌تر: تشویق تکمیل فرم فایل (دیده‌شدگی فایل‌های ناقص را می‌توان بعداً با ضریب اعتماد کاهش داد).
2. **شراکت ذاتاً کم‌داده است** (ارزش زمین مشتری با قیمت مشارکت فایل بُعد مشترک دقیق ندارد) → امتیاز مالی خنثی باقی می‌ماند؛ تطبیق شراکت همیشه «Fair/Good» است نه «Excellent». صادقانه، ولی محدود.
3. **شهر در پروفایل مشتری فعلی ثبت نمی‌شود** (فرم فقط شهرستان/محله می‌گیرد؛ `preferred_city_ids` نوشته نمی‌شود) → سطح شهر در عمل برای مشتریان جدید بی‌عمل است تا فرم تکمیل شود. (تغییر فرم = خارج از این کار، با توافق بعدی.)
4. **ستون `street` در دیتابیس نیست** → سطح خیابان/محدوده غیرقابل محاسبه (مکانش در تختهٔ موقعیت رزرو شده).
5. **۱۸ از ۲۶ امکانات مشتری ستون فایل ندارند** (آتشکده، سونا، کرکره برقی، تابلوخور، سرویس بهداشتی، چاه آب، چهاردیواری، فضای اداری، جرثقیل، آب/برق/گاز…) → همیشه ۰.۵ + ℹ. تا آنکه ستون/JSON امکانات در فایل اضافه نشود، مشتری ویلاییِ «آتشکده‌دار» هرگز امتیاز امکانات کامل نمی‌گیرد.
6. **اتاق:** فایل هم `rooms` و هم `bedrooms` دارد و معنی دقیق ستون‌ها در داده‌های قدیمی مبهم است؛ قرارداد: `bedrooms ?? rooms`.
7. **جدول سازگاری نوع ملک قضاوتی است** (مثلاً «آپارتمان↔خانه ویلایی = partial») — باید توسط شما تأیید/تنظیم شود؛ خوشبختانه یک جدول صریح در `config.ts` است.
8. **VETO ۵۰٪ قیمت ممکن است معاملات «قابل مذاکره» را پنهان کند** (فایل `negotiable=true` با ۴۹٪ عبور رد می‌شود). قاعدهٔ اول شما دقت را ترجیح می‌دهد؛ اگر بعداً بخواهید، می‌توان برای فایل‌های `negotiable` آستانهٔ veto را به ۷۵٪ گسترش داد (یک عدد در config).
9. **تلاقی چند نوع مشتری:** اگر مشتری [آپارتمان، ویلا] باشد، ترجیحات (بودجه/متراژ) از **نوع سازگار برنده** خوانده می‌شود؛ اگر دو نوع سازگاری متفاوت داشته باشند، ممکن است بودجهٔ نوع دوم نادیده گرفته شود. (در عمل فرم، ترجیحات را برای هر نوع جدا می‌گیرد؛ این حالت نادر است ولی صریح می‌شود.)
10. **مقیاس امتیاز حساس به وزن‌هاست:** وزن‌های پیشنهادی (§۵) بر روی دادهٔ واقعی شما کالیبره نشده‌اند؛ بعد از ۲–۳ هفته استفاده واقعی، مقایسهٔ «توصیه‌شده vs واقعاً فروخته‌شده» می‌تواند وزن‌ها را راست‌بینی کند. (همه در یک فایل.)
